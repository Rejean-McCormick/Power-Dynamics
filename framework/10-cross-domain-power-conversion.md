# Cross-Domain Power Conversion

Power is often most consequential when capability or authority in one domain is converted into leverage in another.

## Conversion

A conversion can be represented as:

```text
source resource / puissance
→ conversion mechanism
→ destination resource / puissance / power relation
```

Examples:

```text
knowledge → evidence of competence → credibility
credibility → ranking / endorsement → visibility
visibility → audience → opportunity
money → purchase / funding → infrastructure
infrastructure → dependency → bargaining leverage
brand → affiliation → revenue
administrative control → defaults → de facto policy
```

## Cross-domain leverage

Not all conversion is problematic. Many desirable systems depend on it.

The problem begins when:

1. the conversion is hidden;
2. the destination authority exceeds the source mandate;
3. affected actors cannot contest or substitute;
4. the conversion compounds through multiple domains;
5. the resulting leverage becomes durable or terminal.

## Capture

> **Capture occurs when control over one legitimate function is converted into durable influence over functions outside its intended mandate.**

Canonical warning pattern:

> **Functional Control → Cross-Domain Power**

## Power stacking

Power stacking occurs when one actor or node combines several functions whose interactions create leverage not visible when each function is assessed separately.

For example:

```text
identity
+ credibility
+ discovery
+ funding
+ workflow
= cross-domain leverage
```

or:

```text
monetary rail
+ taxation
+ allocation
+ sanctions
+ dispute enforcement
= high terminality risk
```

## Conversion firewalls

A conversion firewall does not prohibit composition. It prevents **automatic authority inheritance**.

Examples:

- expertise → advice, not sovereignty;
- money → funding, not votes;
- brand → attention, not truth;
- credibility → discoverability, not unquestionable authority;
- infrastructure → capability, not ownership of users;
- execution → mandate implementation, not mandate redefinition.

## Analytical procedure

For each important function:

1. Name the source domain.
2. Name the source resource/capability.
3. Identify the conversion mechanism.
4. Name the destination domain.
5. Identify the resulting power relation.
6. Measure dependency and switching cost.
7. Identify returns and compounding.
8. Identify firewall, contestation, substitution, or exit.
9. Test whether the destination authority is within mandate.
10. Test whether capture of the instance would imply capture of the system.

## Relation to the three-axis model

Cross-domain conversion connects the three axes:

- **ontology** — what changes state;
- **dynamic** — conversion / compounding / capture;
- **domain** — where the source and destination operate.

This is why the domain axis must be explicit rather than a loose list of examples.
