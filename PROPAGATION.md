# Propagation and Coupled Compounding

Power Dynamics already explains how capability is formed, mobilized, composed, converted, preserved, compounded, routed, contested, and replicated.

This page adds the missing systems-level question:

> **How does capability in one branch make capability elsewhere easier to activate, and what happens when several such loops reinforce one another?**

## 1. Compounding is not propagation

**Compounding** means that action leaves returns that increase later capability in the same actor, branch, or system.

```text
A capability
→ action
→ result
→ reusable return
→ greater future A capability
```

**Propagation** means that capability or returns from one locus reduce the activation cost, increase the expected value, or supply resources for capability to emerge elsewhere.

```text
A capability
→ reusable return
→ lower activation barrier for B
→ B capability emerges or strengthens
```

**Coupled propagation** appears when several loops exchange returns:

```text
A strengthens B
B strengthens C
C returns assets to A
```

The system can then grow by **conversion between loops**, not only by repetition inside one loop.

## 2. The kOA propagation thesis

kOA is unusually propagation-oriented because different branches can generate different reusable returns:

- software and tooling;
- knowledge and documentation;
- credibility and evidence;
- relationships and institutional access;
- money and service revenue;
- operators and teaching capacity;
- language coverage;
- integrations and compatibility;
- content and demonstrations;
- reputation and brand recognition;
- machine-readable context;
- deployment experience and operational memory.

The important property is not simply that each branch can grow.

> **Returns generated in one branch can often be routed into another branch.**

Examples:

```text
service revenue
→ development capacity
→ better tooling
→ lower deployment cost
→ more deployments
→ more service revenue
```

```text
successful pilot
→ evidence
→ credibility
→ institutional access
→ additional pilots
→ more evidence
```

```text
new operator
→ independent deployment
→ reduced founder dependency
→ more simultaneous deployments
→ more training cases
→ better operator formation
```

```text
new integration
→ broader capability surface
→ more useful deployments
→ more reasons for other systems to integrate
```

## 4. Coupling matters more than the number of loops

A list of fourteen independent flywheels is not yet a propagation architecture.

The stronger condition is **cross-loop convertibility**.

```text
TECHNICAL CAPABILITY
        ↓
useful product
        ↓
WORLD / DEMO
        ↓
understanding
        ↓
pilot
        ↓
real evidence
   ↙         ↘
credibility   operational demand
   ↓               ↓
access          managed service
   ↓               ↓
new pilots       revenue
   ↘               ↙
    greater development capacity
               ↓
       greater technical capability
               ↺
```

A second loop can attach:

```text
pilot
→ documented method
→ UCKK / operator formation
→ independent operator
→ additional deployment
→ more cases for training
```

A third can attach:

```text
deployment
→ more objects / judgments / evidence
→ SmartVote signal
→ better discovery
→ higher utility
→ more deployment interest
```

The multiplication effect comes from **shared returns**.

## 5. Branch asymmetry: local failure, exportable success

A modular branch ecology can create a useful asymmetry:

```text
branch failure
→ primarily local loss

branch success
→ potentially exportable returns
  (money, evidence, code, credibility, users, methods, integrations)
→ benefits elsewhere
```

This is only true when boundaries remain real. Hidden coupling can turn local failure into systemic failure.

Propagation therefore depends on the same constitutional requirements as the rest of Power Dynamics:

- explicit authority boundaries;
- portable evidence and artifacts;
- no automatic cross-domain sovereignty;
- substitutability and exit;
- local operational autonomy where practical;
- inspectable conversion paths.

## 6. Reflexive propagation: kOA can be used to develop kOA

A special case is **movement / ecosystem self-use**.

If a multi-actor kOA initiative uses its own systems for proposals, ranking, work routing, knowledge preservation, training, and publication, then the deployment environment becomes a continuous integration test for the sociotechnical architecture.

```text
contributors
→ Konnaxion / SmartVote
→ priorities
→ Orgo
→ work
→ results
→ Kristal / documentation
→ UCKK
→ new operators
→ more contributors
→ better kOA
→ more capable collaboration
↺
```

This loop is not evidence until multiple actors use it in practice. It is nevertheless a particularly strong falsifiable design target.

## 7. Founder decentering is part of propagation, not only governance

Founder-specific knowledge can be converted into shared capability:

```text
founder knowledge
→ documentation / schemas / tests / protocols
→ independent mastery
→ more parallel work
→ less founder bottleneck
```

The decisive resilience property is not pseudonymity.

A persona or pseudonym can manage exposure and preserve narrative optionality. It does **not** make the system independent.

System independence requires:

- other maintainers;
- independent deployment;
- portable keys / governance where appropriate;
- explicit protocols;
- reproducible builds and recovery;
- documentation sufficient for outsiders;
- legitimate disagreement and fork paths.

A useful test is:

> **Can the founder become temporarily unavailable without halting operation, interpretation, deployment, governance, or transmission?**

## 8. Positive feedback must have governors

Propagation without damping becomes capture, runaway growth, noise, or fragility.

Important governors include:

```text
expertise grows
→ keep expertise domain-bounded

credibility grows
→ credibility ≠ sovereignty

money grows
→ funding ≠ political standing

brand grows
→ brand ≠ protocol authority

integration grows
→ preserve system authority boundaries

AI throughput grows
→ AI remains bounded and non-authoritative

content grows
→ provenance / validation / publication gates

federation grows
→ local exit / fork / autonomy remain practical

founder recognition grows
→ founder ≠ constitutional authority
```

The target is not maximum acceleration.

> **Healthy propagation increases distributed capability faster than it increases terminal dependency.**

## 9. Evidence ladder

Propagation claims should move through explicit evidence levels.

```text
DESIGNED
→ DEMONSTRATED
→ USED
→ REPEATED
→ INDEPENDENTLY REPLICATED
→ FEDERATED / CROSS-BRANCH
```

A World is evidence that a context can be represented.
It is not proof of adoption.

A cinematic tour is evidence that a demonstration can be generated.
It is not proof that a viewer understood or converted.

A pilot is evidence of bounded use.
It is not proof of independent replication.

The strongest propagation evidence appears when another actor reproduces useful capability without founder mediation.

## 10. Canonical propagation tests

For any proposed loop, ask:

1. What is the input asset?
2. What conversion occurs?
3. What reusable return is produced?
4. Who receives that return?
5. Which other loop can consume it?
6. Does the return lower activation cost elsewhere?
7. Does the loop reduce or increase dependency?
8. What damping mechanism prevents runaway conversion?
9. What observation would falsify the loop?
10. Can the loop close without founder intervention?
