# kOA Adoption Stack

Adoption is not one event. It is a sequence of barriers.

```text
NOTICE
→ UNDERSTAND
→ TRUST ENOUGH TO EXAMINE
→ SEE LOCAL RELEVANCE
→ TRY
→ DEPLOY
→ GET LOCAL VALUE
→ REPEAT
→ OPERATE INDEPENDENTLY
→ CONNECT / FEDERATE IF USEFUL
```

Different kOA mechanisms attack different barriers.

| Barrier | Candidate mechanism | Intended effect |
|---|---|---|
| Notice | books, music, podcasts, public essays, targeted outreach | create an entry path |
| Complexity | progressive documentation, cinematic tours, concise briefs | reduce explanation cost |
| Abstractness | Worlds / scenario seeding | make the system legible in a familiar context |
| Trust | public code, tests, provenance, explicit limitations | reduce belief dependence |
| Local relevance | Scenario Mosaic / domain patterns | connect general architecture to a real workflow |
| Deployment | Capsule Manager / Koali tooling | reduce technical activation cost |
| Lock-in fear | self-hosting, export, fork, local authority | preserve optionality |
| Language | SemantiK / multilingual tooling | reduce semantic access barriers |
| Operator scarcity | UCKK / runbooks / documentation | reproduce human capability |
| Integration cost | Kintsugi boundaries / annexation | reuse existing systems instead of replacing them |
| Ongoing operations | managed service | sell responsibility rather than permission |

The strongest adoption architecture does not require every actor to pass through the same corridor.

A researcher may enter through knowledge infrastructure.
A language organization may enter through multilingual capability.
A municipality may enter through a concrete workflow.
A developer may enter through code.
A cultural institution may enter through provenance and stewardship.

These paths should converge on the same inspectable core rather than becoming disconnected narratives.
