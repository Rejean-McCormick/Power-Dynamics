# Cross-Branch Returns

A modular ecosystem becomes strategically unusual when branch returns can cross branch boundaries.

## Return classes

| Return | Example origin | Example destination |
|---|---|---|
| Money | managed hosting / support / merchandise | engineering, documentation, public-good infrastructure |
| Code | internal tooling | multiple repositories |
| Evidence | institutional pilot | credibility for another branch |
| Credibility | academic / technical validation | institutional access elsewhere |
| Relationships | one sector | introductions into another sector |
| Knowledge | operational use | documentation, Kristal, training |
| Operators | UCKK / apprenticeship | deployments, support, integration |
| Language assets | SemantiK work | Konnaxion, UCKK, public communication |
| Integrations | Kintsugi | wider system capability |
| Content | Worlds / scenarios | demos, education, tests |
| Brand attention | cultural layer | discovery of technical assets |
| Technical legitimacy | public repositories / tests | confidence in nontechnical initiatives |

## Strategic asymmetry

A desirable branch architecture tries to make:

```text
failure costs local
success returns portable
```

This is never automatic. Shared infrastructure, brand, funding, identity, or governance can make failure systemic.

The audit question is therefore:

> **Which branch dependencies are intentionally shared, and which are only accidentally shared?**

## Cross-subsidy without capture

Cross-branch funding can be productive:

`Branch A revenue → shared infrastructure → Branch B capability`

But economic return should not silently purchase unrelated authority.

`funding → capability` can be legitimate.

`funding → political or epistemic sovereignty` requires an explicit constitutional basis and should normally be blocked.
