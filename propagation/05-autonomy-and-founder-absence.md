# Autonomy and Founder Absence

Founder decentering is both a constitutional requirement and a throughput mechanism.

If every deployment, interpretation, integration, conflict, or public explanation requires one founder, growth increases bottleneck pressure faster than capacity.

## Founder-to-protocol conversion

```text
founder skill
→ method
→ documentation
→ schema / test / tool
→ independent operator
→ parallel capability
```

The objective is not founder disappearance. It is to make founder participation **optional rather than structurally mandatory**.

## Absence test

A strong propagation system should eventually answer yes to questions such as:

- Can another person install it?
- Can another person restore it?
- Can another person explain its core model accurately?
- Can another person train the next operator?
- Can governance continue without founder voting or interpretation?
- Can a branch reject a founder preference?
- Can an institution leave without founder permission?
- Can development continue during founder inactivity?

## Persona / pseudonym distinction

An architect may use a pseudonym or narrative persona to preserve creative freedom, manage exposure, or create a separate cultural surface.

That does **not** by itself make the system resilient to criticism or personal attack.

Resilience comes from:

- independent evidence;
- distributed maintainership;
- forkability;
- source availability;
- explicit authority boundaries;
- reproducible operations;
- plural interpretation;
- continued function during founder absence.

The useful separation is therefore:

```text
persona → exposure / narrative optionality
protocolization → technical and institutional autonomy
```
